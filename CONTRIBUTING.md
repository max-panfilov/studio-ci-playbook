# Участие в разработке

## Что можно предложить

Полезны уточнения архитектуры, новые отрицательные сценарии, исправления ссылок и диаграмм, улучшение схем синтетических примеров и перевод неясных формулировок на точный технический русский. Изменение не должно превращать документарный репозиторий в скрытую копию private CI/CD.

Перед работой прочитайте `AGENTS.md`, `SANITIZATION.md` и `docs/limitations.md`. Для спорного примера сначала опишите, какую идею он иллюстрирует и почему не раскрывает реальную инфраструктуру.

## Порядок изменения

1. Создайте отдельную ветку и сохраните чужую незавершённую работу.
2. Внесите узкое изменение. Не смешивайте редакционную правку с изменением контракта примеров.
3. При изменении JSON обновите публичную схему и тесты. При изменении YAML сохраните YAML 1.2 и запрет duplicate keys.
4. Проверьте статусы утверждений: approved policy, dated observation, synthetic example или limitation. Наблюдение не повышайте до общей нормы без отдельного решения владельца.
5. Выполните проверки на доверенном self-hosted runner по `docs/verification.md`. Приложите фактические результаты и ограничения, не пишите «всё проверено» по предположению.
6. Откройте pull request с описанием мотива, изменённых документов, проверок и оставшихся неизвестных.

Обновляйте `uv.lock` только на доверенном self-hosted CI и проверяйте `uv sync --frozen`. Не добавляйте runtime-зависимости и не запускайте приложение ради документационной правки. Автоматический merge и production effects этот репозиторий не требует.

## Требования к примерам

Все JSON в `examples/` обязаны содержать:

```json
{
  "synthetic": true,
  "evidence": false
}
```

Используйте только разрешённые placeholder SHA/digests, nil UUID, нулевые run/attempt IDs, вымышленный `example-org` и хосты в зоне `.invalid`. Пример обязан быть достаточно полным для обучения, но не должен становиться действительным release receipt.

`examples/gitea-ci.yml` остаётся схематичным и непригодным для запуска. Не заменяйте placeholders рабочими адресами, секретами, настоящими runner labels или deployment командами.

## Текст и диаграммы

Соблюдайте русскую типографику: «кавычки-ёлочки», тире — с пробелами, диапазоны 10–15 без пробелов, неразрывные пробелы после однобуквенных предлогов и десятичные запятые. Убирайте канцелярит и рекламные оценки. Числа сопровождайте датой, workload и границей вывода.

Диаграммы Mermaid вставляйте непосредственно в нужный документ. Не создавайте отдельные дублирующие источники диаграмм. Проверяйте не только синтаксис, но и смысл стрелок, границы доверия и читаемость после публикации.

## Сообщение об уязвимости

Не отправляйте секреты и частные сведения в публичный issue. Следуйте `SECURITY.md`; случайно добавленный секрет не пытайтесь скрыть последующей правкой — нужны отзыв credential и отдельная проверка истории.
